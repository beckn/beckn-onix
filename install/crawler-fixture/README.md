# Local verification

A stack for checking that the catalog crawler actually works. No real publisher
CDN, no hand-built Postgres, no hand-made signatures.

`install/docker-compose-crawler.yml` brings up three things:

| Service            | What it is                                                                  |
| ------------------ | --------------------------------------------------------------------------- |
| `crawler-postgres` | The crawler's own Postgres. Migrations are applied by the crawler on start.  |
| `publisher-origin` | An nginx serving `crawler-fixture/publisher` as a publisher's CDN.           |
| `onix-crawler`     | The onix adapter built from this repo with plugins, crawl module only.       |

## Read this before you start

**This stack is not self-contained, and it cannot be made self-contained.** Two
services it depends on live outside it. Skip either one and you will watch a
crawl fail for a reason that is nothing to do with the crawler.

**1. A network registry.** The crawler verifies every catalog file against the
publishing participant's signing key **as held in the network registry**. Keys
are never configured locally, and verification cannot be turned off. So:

- the adapter **will not start** without a registry plugin block. It is already
  in `crawler-fixture/onix-crawl.yaml`;
- the registry it points at is **not started by this compose file**;
- until that registry is reachable and holds the fixture publisher's key, every
  catalog file fails key resolution. The sync retries with backoff and then
  parks.

**2. The Discovery Service.** It lives in `beckn-discovr` and runs its own
Postgres, Kafka and Elasticsearch. It is started from that repo and reached over
the shared `beckn-network`.

Everything before the key lookup does run without either of them: the index is
polled, change detection runs, and the catalog is queued. That is worth watching
on its own. It is just not a completed crawl.

## What the registry has to hold

The record is committed as `registry-subscription.json` and regenerated by the
same command as everything else:

```json
{
  "subscriber_id": "sunrise-ev.example.org",
  "key_id": "fixture-key-1",
  "signing_public_key": "V6FwanXNHoN2lNmzQVCbpjr4r3fDyopwSoINlSNOqMw=",
  "status": "SUBSCRIBED"
}
```

Every field matters, so here is what each one has to line up with.

| Field                | Must equal                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| `subscriber_id`      | `participantId` at the top of `publisher/catalog-index.json`. That is the lookup's subscriber.      |
| `key_id`             | `signature.keyId` on every file entry in that index. That is the lookup's key.                      |
| `signing_public_key` | The fixture publisher's public key, **standard base64 with padding**, decoding to 32 raw bytes.     |
| `status`             | Anything except `EXPIRED`, `UNSUBSCRIBED` or `INVALID_SSL`. Those three verify nothing.             |

Two details that are easy to get wrong:

- The key is **standard** base64, not base64url. `fetch/verify.go` decodes it
  with `base64.StdEncoding`. A base64url copy of the same key fails to decode
  and parks the catalog.
- `key_id` is a plain token with no `#` in it, on purpose. The dediregistry
  client interpolates the key id straight into a lookup URL path with no
  escaping, so a `#` would be read as a URL fragment and truncate the lookup.

**Registering this is a manual step and this fixture does not automate it.** How
you register depends on which registry you run, and this repo does not ship a
registry whose admin flow can be scripted from here. Do not expect
`docker compose up` to do it.

## Prerequisites

1. Docker with Compose v2.

2. The shared network:

   ```bash
   docker network create beckn-network
   ```

3. **A registry, reachable from `onix-crawler`, holding the record above.**

   `crawler-fixture/onix-crawl.yaml` is configured for the `registry` plugin at
   `http://registry:3030/subscribers`, which is the local registry in
   `install/docker-compose-registry.yml` addressed by container name. That
   compose file puts the container on a network called `beckn_network`, with an
   underscore, which is **not** the `beckn-network` this stack joins. So after
   starting it, attach it:

   ```bash
   docker compose -f install/docker-compose-registry.yml up -d
   docker network connect beckn-network registry
   ```

   Then load the fixture publisher's key into it, by whatever subscribe or admin
   path that registry offers. If you run a different registry, change the `id`
   and `url` in the `registry` plugin block instead.

   Without this step the crawl reaches key resolution and stops there. See
   [When the registry is missing or wrong](#when-the-registry-is-missing-or-wrong).

4. **beckn-discovr running on `beckn-network`.** The push leg needs it.

   ```bash
   cd ../beckn-discovr && docker compose up -d
   ```

   The crawler pushes to `http://discovr-ingestion:8080/catalog/push`, which is
   `discovr-ingestion`'s in-network address.

   Discovery verifies Beckn HTTP signatures on `/catalog/push` by default, and
   the crawler's push client does not sign. So for local verification whitelist
   that one endpoint in `beckn-discovr`'s compose:

   ```
   SIGNATURE_WHITELISTED_ENDPOINTS=POST:/catalog/push
   ```

   Without it every push comes back 401.

## Run it

From the repo root:

```bash
docker compose -f install/docker-compose-crawler.yml up --build
```

That builds the adapter with plugins (`Dockerfile.adapter-with-plugins`), waits
for Postgres and the publisher origin to go healthy, and starts the crawler with
`CRAWLER_ENABLED=true`.

Watch it:

```bash
docker compose -f install/docker-compose-crawler.yml logs -f onix-crawler
```

A first pass looks like this. The index job runs on startup, then the catalog
job drains the queue on the next tick:

```
"component":"daemon" "stage":"ready"    "key_source":"registry" "sources":1
"component":"crawl"  "stage":"polled"   "result":"updated" "version":2
"component":"crawl"  "stage":"queued"   "catalog_id":"cat-ev-001" "op":"sync"
"component":"crawl"  "stage":"finished" "indexes":1 "updated":1 "queued":1
"component":"sync"   "stage":"syncing"  "catalog_id":"cat-ev-001"
"component":"sync"   "stage":"synced"   "catalog_id":"cat-ev-001" "mode":"MERGE"
"component":"sync"   "stage":"finished" "synced":1 "failed":0
```

Filter on the fields, not on `msg`. The message strings are written for humans
and contain punctuation that is awkward to grep for.

Inspect what was persisted:

```bash
docker exec crawler-postgres psql -U crawler -d crawler \
  -c 'select index_url, index_version, sync_status from crawler_index;' \
  -c 'select catalog_id, version, status from crawler_catalog;' \
  -c 'select count(*) from crawler_queue;'
```

Trigger an immediate re-crawl instead of waiting for the 30s tick:

```bash
curl -sS -X POST localhost:8081/crawl \
  -H 'Content-Type: application/json' \
  -d '{"indexUrl":"http://publisher-origin/catalog-index.json"}'
```

That URL has to be one of the `CRAWLER_INDEX_URLS` the crawler was started with.
The handler checks the request against that list and answers `403` otherwise.

Look at the fixture the crawler is reading:

```bash
curl -s localhost:8088/catalog-index.json
curl -s localhost:8088/catalogs/cat-ev-001-v1.json
```

Tear down, including the crawler's database volume:

```bash
docker compose -f install/docker-compose-crawler.yml down -v
```

## When the registry is missing or wrong

This is the most likely way a run of this fixture goes wrong, so it gets its own
section.

**No registry plugin block at all.** The adapter does not start. The crawl
handler refuses to construct and says the registry plugin is required.

**Registry configured but unreachable.** Key resolution cannot answer, and an
unreachable registry says nothing about the file, so this is treated as
**transient**. The catalog retries with backoff, and after `CRAWLER_MAX_ATTEMPTS`
attempts (5 here) it parks. Look for `component=sync stage=failed`
`fault=transient`, then `will_retry=false` on the last one.

**Registry reachable but the key is not in it.** That is a definitive answer, so
it is **permanent**. The catalog parks immediately with `fault=signature` and
does not retry until the publisher publishes a new version.

All the signature verdicts land on `component=sync stage=failed` with
`fault=signature`. The `error` field carries the specific cause:

| `error` contains                                          | Cause                                                                             |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `registry has no key ... for subscriber ...`              | The record was never registered, or `key_id` / `subscriber_id` do not match the index. |
| `has unusable status`                                     | The subscription is `EXPIRED`, `UNSUBSCRIBED` or `INVALID_SSL`.                        |
| `has no signing public key`                               | The record exists but carries no key.                                                  |
| `is not valid base64` / `decodes to N bytes, want 32`     | The key was registered as base64url, truncated, or is not an Ed25519 key.              |
| `index declares no participantId`                         | `participantId` is missing from the index. Nothing to look the key up under.           |
| `has no signature`                                        | A file entry in the index lost its `signature` block.                                  |
| `signature is not bound to a catalog`                     | The entry was not stamped with its `catalogId`. Regenerate the index.                  |
| `signature expired at ...`                                | `validUntil` is in the past. Regenerate the index.                                     |
| `signature verification failed`                           | A catalog file, digest, URL or `validUntil` was edited by hand.                        |

One thing that will confuse you if nobody warns you: the human-readable message
on all of these says the crawler could not send the catalog to Discovery.
Nothing was sent, and nothing was even fetched, because the gate runs before the
GET. The message is built from a fault-to-phrase table that has no `signature`
entry yet, so it falls to the default. Trust `fault=signature`, not the
sentence.

A separate failure, not a signature one:

| Log                | Cause                                                       |
| ------------------ | ------------------------------------------------------------- |
| `digest mismatch`  | A catalog file changed without the index being regenerated. |

The fix for anything hand-edited is always `go run ./install/crawler-fixture/gen`.

## What is in the fixture

`publisher/` is what nginx serves, so its layout is the publisher's URL layout.

| File                                          | Role                                                                                               |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `publisher/catalog-index.json`                | The index. Participant `sunrise-ev.example.org`, index version 2, one public catalog `cat-ev-001`.  |
| `publisher/catalogs/cat-ev-001-v1.json`       | Baseline, version 1. Two resources, one offer.                                                      |
| `publisher/catalogs/cat-ev-001-v1-to-v2.json` | Change file, version 1 to 2. Updates `res-chg-002`, adds `res-chg-003`.                             |
| `registry-subscription.json`                  | The record that must exist in the registry for this fixture to verify. Nothing reads it at runtime.  |
| `fixture-signing-key.json`                    | The publisher's keypair, including the private half. See the warning below.                          |
| `gen/main.go`                                 | The generator. Recomputes keys, digests, sizes and signatures.                                       |

`registry-subscription.json` is documentation with exact values, not a config
file. No process loads it. It exists so the key an operator registers is copied,
not retyped.

A first crawl exercises both catalog files. The cursor starts behind the
baseline, so the baseline is fetched and the change file is folded onto it. That
gives three resources and one offer, pushed as a MERGE.

### About the committed private key

`fixture-signing-key.json` contains a private key. It is committed on purpose
and it is not a credential. It signs nothing but this fixture, it is trusted by
nothing but this fixture, and it is derived deterministically from a seed label
printed in the same file, so anyone can regenerate it in one command. Never
reuse it anywhere, and never treat a report of it leaking as an incident.

### The digests are real

They are the sha-256 of the exact file bytes nginx serves:

```
sha-256:07a6646e9482e196777b75996280b5407c74fda81364f46c95820fc82b1ad128  catalogs/cat-ev-001-v1.json
sha-256:c7af97b69cf98c87ca00632103628e8e7fe400739f64b4474946d985e357be25  catalogs/cat-ev-001-v1-to-v2.json
```

Check them yourself:

```bash
shasum -a 256 install/crawler-fixture/publisher/catalogs/*.json
```

### The signatures are real

Each index entry carries an Ed25519 signature over the tuple
`{catalogId, version, url, digest, validUntil}`. That is the tuple defined by
`pkg/security/artifactverifier.VerifyFileTuple`, which is exactly what the
crawler's fetch gate calls. The signatures are produced by
`pkg/security/artifactsigner.SignFileTuple` and re-verified before they are
written out, so the generator cannot emit an index the crawler would reject on
the signature itself.

What the generator cannot do is put the key in your registry. A signature that
is mathematically perfect still parks the catalog if the verifying key is not
registered.

nginx sends `ETag` and `Last-Modified`, so leaving the stack running also
exercises the conditional-GET path. Later index polls come back 304 Not Modified
and are logged as `"result":"not_modified"`.

## Regenerating the fixture

Edit a catalog file and its digest, its size and its signature all go stale at
once. Do not patch them by hand. Run:

```bash
go run ./install/crawler-fixture/gen
```

That one command rewrites `publisher/catalog-index.json`,
`registry-subscription.json` and `fixture-signing-key.json`, and prints the
`subscriber_id`, `key_id` and `signing_public_key` to register. Everything it
writes is derived from the files on disk:

- digest and size come from hashing the catalog file bytes;
- each signature is signed with `artifactsigner.SignFileTuple`;
- each signature is then re-checked with `artifactverifier.VerifyFileTuple`
  before anything is written.

The keypair is derived from a fixed seed label, `seed = sha256(seedLabel)`, so
re-running gives byte-identical output and the committed signatures stay valid.
It is a real Ed25519 keypair. It is simply not a random one, because a random
one would invalidate the committed index on every run.

Because the key is stable, re-running the generator does not invalidate what you
registered. Changing `seedLabel`, `keyID` or `participantID` does, and you have
to register again.

One thing the generator does not do: bump the index version. If you want an
already-running crawler to notice your edit, raise `indexVersion` in
`gen/main.go`. Change detection compares the index version against the stored
one, and an unchanged version is skipped.

## Why the fixture network uses 203.0.113.0/24

The crawler refuses any publisher URL that resolves to a loopback, private,
link-local or CGNAT address. That is the SSRF guard in
`internal/crawler/fetch/guard.go`, and it has no env switch. `AllowPrivateFetch`
is a test-only `Option`. A default Docker bridge hands out `172.16/12`
addresses, which the guard rejects, so a naive compose file can never crawl its
own fixture.

The fixture network is therefore pinned to `203.0.113.0/24`, which is RFC 5737
TEST-NET-3. That range is reserved for documentation, never routed on the public
internet, and not in any range the guard treats as private. `publisher-origin`
sits at a fixed `203.0.113.10`. This keeps the guard fully enabled in the
verification stack rather than working around it.

The guard applies to **publisher fetches only**. The registry lookup goes
through the registry plugin's own HTTP client, so a registry on an ordinary
private Docker address is fine.

## Configuration

Every `CRAWLER_*` variable has a working value in the compose file, so the stack
runs with no `.env`. Override any of them from the shell or a `.env` next to the
compose file. The ones worth knowing:

| Variable                   | Value in the fixture                                                       | Note |
| -------------------------- | -------------------------------------------------------------------------- | ---- |
| `CRAWLER_ENABLED`          | `true`                                                                      | Off by default everywhere else. Turning it on is what makes the DSN, the push endpoint and the index URLs required. |
| `CRAWLER_STORE_PROVIDER`   | `postgres`                                                                  | Names a registered store backend. `postgres` is the only one registered. |
| `CRAWLER_DB_DSN`           | `postgres://crawler:crawler@crawler-postgres:5432/crawler?sslmode=disable`  | Local throwaway credentials. |
| `CRAWLER_PUSH_ENDPOINT`    | `http://discovr-ingestion:8080/catalog/push`                                | Discovery on `beckn-network`. |
| `CRAWLER_INDEX_URLS`       | `http://publisher-origin/catalog-index.json`                                | Comma-separated. The only source, and the allowlist `/crawl` checks against. |
| `CRAWLER_INDEX_INTERVAL`   | `30s`                                                                       | Production default is 5m. |
| `CRAWLER_CATALOG_INTERVAL` | `5s`                                                                        | Production default is 30s. |
| `CRAWLER_NETWORK_IDS`      | empty                                                                       | The sample catalog is public. |
| `CRAWLER_BPP_URI`          | `http://onix-crawler:8081`                                                  | Goes on the push context as `bppUri`. |

There is **no variable for signing keys**. Keys come from the registry plugin.

Do **not** set `CRAWLER_REGISTRY_URL`. It means a registry used as a source of
indexes to crawl, which is a different feature from the registry key lookup this
fixture needs. It is not implemented, and a non-empty value fails startup rather
than being ignored.

Host ports, all overridable: `ONIX_HOST_PORT` 8081, `PUBLISHER_HOST_PORT` 8088,
`CRAWLER_DB_HOST_PORT` 5439.

The adapter config is `onix-crawl.yaml`. It registers only the crawl module, so
the stack does not need the vault, redis or otel-collector that the full BAP and
BPP configs pull in. It does need the registry plugin, which is not optional.
The crawler plugin reads env first and falls back to that file, so the compose
file is the single place to change the `CRAWLER_*` settings.
